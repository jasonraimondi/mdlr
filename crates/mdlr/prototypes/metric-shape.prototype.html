Metric Shape Prototype

Four ways of scoring the same code, driven by the moves a coding agent actually makes. Throwaway — this page exists to settle one argument.

The question this answers mdlr scores each function on a one-sided curve: bigger is worse. An agent told to lower the score can do it two ways — really simplify the code, or shuffle the code around until it falls off the readout. function_size already has a two-sided curve (bad when too big and bad when too small) to catch one kind of shuffling. Does that curve hold up against the other moves? And what shape catches the move it misses — splitting one big function into ten small ones — without also punishing code that is honestly made of small pieces?
